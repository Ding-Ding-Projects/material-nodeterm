# Proxy and isolated debugging browser sessions

**Category:** [Browser](./README.md)

The isolated debugging browser node starts a supported Chromium browser in a fresh profile,
optionally routes its page through a validated proxy, and exposes a loopback-only DevTools
Protocol endpoint for local tooling. It is a clean-room feature: it does not copy or depend on
another product's implementation, assets, or operation names.

## Behaviour

Use **New isolated debugging browser…** from the canvas context menu. The node provides guided
controls for a session name, an `http` or `https` start URL, and an optional proxy. Proxy choices
are limited to `http`, `https`, `socks4`, and `socks5`; the host and port are validated before the
session can start. A browser executable is selected from the detected Microsoft Edge, Google
Chrome, or Chromium entries. The UI does not accept a command line, extra flags, script text, or a
free-form executable path.

Each start creates a new profile directory owned by nodeterm. The launch uses fixed isolation
flags, disables sync and extensions, and binds the debugging HTTP endpoint to `127.0.0.1`. The
node waits for the browser's target list and accepts it only when the response contains exactly
one `page` target whose URL matches the requested start URL exactly and whose websocket endpoint
is loopback. A second tab, extension target, restored page, non-loopback endpoint, or mismatched
URL is an isolation failure, not a target to pick conveniently.

The endpoint is displayed only as live machine-local status. Stopping the node terminates the
owned child and removes the fresh profile directory. Closing the app stops all sessions it owns.

## Portable project data

The project projection stores only a versioned intent record: the display label, the normalized
HTTP(S) start URL, and the proxy scheme, host, and port. It never stores cookies, local storage,
browser profile directories, process ids, local ports, websocket URLs, normal-browser profile
paths, provider sessions, or credentials. Runtime bindings are held in the machine-local
`LocalNodeExec` overlay when needed and are stripped from project files and peer mutations.

Import is data-only. It does not start a browser, make a proxy request, open a CDP connection,
download a browser, or mutate an external provider. On another computer the node presents the
normal Configure or Leave Unbound route until the user starts it there.

## Configuration and recovery

- **Session name:** a bounded local label, persisted as safe project metadata.
- **Start URL:** an HTTP(S) URL without embedded userinfo. File, script, data, and custom schemes
  are refused.
- **Proxy:** optional scheme, DNS or IP host, and port 1 through 65535. Userinfo, path fragments,
  control characters, malformed IPs, and out-of-range ports are refused.
- **Browser choice:** the detected supported executable list. A stale or manually supplied path is
  not accepted as an executable override.
- **Profile lifecycle:** a fresh profile is created per run and deleted on stop. The user's normal
  browser profile is never reused, even when a session uses the same browser vendor.

If the selected browser is unavailable, the node remains usable for editing the safe intent and
explains that no supported executable was detected. If startup times out or the target list fails
the exact isolation rule, the child is stopped, its profile is removed, and the node reports the
failure. A retry creates a new disposable profile rather than reusing a possibly contaminated one.

## Security considerations

The proxy is transport configuration, not an authentication channel. Credentials are not accepted
in the proxy host field or URL and are not stored by this feature. CDP is a powerful local control
surface, so the endpoint is always bound to loopback and is never included in portable metadata.
Target validation requires an exact one-target response, rather than using the first matching page;
this prevents normal-profile tabs, extension pages, and restored user state from becoming
debuggable by accident.

Only fixed browser flags are generated by `buildDebugBrowserLaunchArgs`. The renderer cannot append
flags, inject a shell command, select an arbitrary executable, or choose a non-loopback address.
The service owns only the child process and profile directory it created.

## Feature records

| Surface | Implementation | Safe persistence | Runtime-only state |
| --- | --- | --- | --- |
| Shared contract | `src/shared/browser-debug.ts` | `DebugBrowserSpec` | `DebugBrowserBinding` |
| Desktop owner | `src/main/browser-debug-session.ts` | none | child process, profile, loopback endpoint |
| Canvas node | `src/renderer/nodes/DebugBrowserNode.tsx` | `CanvasNodeState.debugBrowserSpec` | live session summary |
| IPC bridge | `src/shared/ipc.ts`, `src/preload/index.ts` | none | executable discovery and lifecycle calls |

The Server Edition and relay bridges do not expose the desktop process owner. They keep the node's
safe intent visible and report that starting an isolated desktop session is unavailable in that
surface, rather than pretending a browser tab can own a local process or CDP endpoint.

## Verification

The focused verification for this feature must exercise proxy scheme, host, port, and URL bounds;
fixed-argument generation; portable projection stripping; fresh-profile lifecycle; exact one-target
validation; loopback-only endpoints; normal-profile non-reuse; startup timeout cleanup; and a real
packaged desktop run. This ultra-speed implementation lane intentionally leaves tests, builds,
packaging, installer execution, runtime interaction, and captures to the release orchestrator.
