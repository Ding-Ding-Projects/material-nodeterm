# GitLab Server hosting

This node deploys a private GitLab Server through the existing guided Docker context manager. It offers the official Community Edition or Enterprise Edition image, pinned by digest, and never accepts arbitrary images, commands, entrypoints, environment text, or public bindings.

## Behaviour

Choose a discovered local or SSH Docker context, then choose Community Edition or Enterprise Edition. The node pulls the selected pinned image, creates four managed volumes for configuration, logs, data, and backups, and starts the server with bounded resources, dropped capabilities, and loopback-only HTTP and SSH ports. Readiness is checked through GitLab's own `/-/readiness` endpoint.

The lifecycle controls are Deploy, Back up, Restore, Update, and Roll back. Restore and rollback use the existing two-key destructive confirmation surface. Backups are enumerated from the managed backup volume, and a backup must be selected from that list before restore is enabled. Long-running actions report queued, running, completed, failed, and cancelled states with progress.

GitLab backup rows carry the shared hosted-resource backup framework descriptor, including product
version, edition, service kind, source, ownership, and resource identity. Backup identifiers pass
the shared safe archive-path validator before they can reach Docker. Restore rechecks that the
selected backup still belongs to the current verified GitLab resource before invoking the native
GitLab restore operation.

After readiness, the user may request one initial root credential handoff. The password is read in memory from GitLab's one-time file and returned only to the active UI. It is never logged, persisted, exported, broadcast as progress, or written into the project file. The UI makes the expiry and one-session visibility explicit.

## Portable and local state

`gitlabHostingConfig` stores schema version, edition, the pinned image reference, loopback binding, and the selected HTTP and SSH port choices in the portable canvas projection. Docker context names, container and volume identifiers, backup files, credentials, readiness state, and process state remain machine-local. Import only hydrates the blueprint and performs no network call, deployment, provider mutation, process launch, or download. The node opens with an explicit Configure and Deploy path on a new machine.

## Guided controls and accessibility

Discovered Docker contexts and backups are searchable lists. Each list has an isolated plain-text-first search field with its own adjacent anchored full regex builder. Edition, binding, port, and lifecycle choices are closed controls populated from known safe values. There is no shell field, raw request editor, arbitrary image input, or free-form port entry. Disabled actions name the missing context, readiness, backup, or current job condition.

The panel uses Material Design 3 tokens, keyboard-operable buttons, visible focus, screen-reader labels and states, bounded internal scrolling, and responsive volume and backup rows. Status and progress are non-blocking and remain reviewable in the operation history.

## Failure modes and recovery

- A missing Docker context leaves the node unconfigured and names the next action.
- A stopped or unready container is shown as stopped or unready rather than healthy.
- A readiness failure keeps the last valid container and offers refresh; it never claims the service is ready.
- A failed update keeps the previous container name for the rollback route.
- A missing, malformed, or expired initial credential file reports that GitLab has not published a credential yet; no partial value is applied.
- A Server Edition or relay session without the local Docker manager reports its unsupported boundary instead of showing fake success.

## Security considerations

Only allowlisted pinned official images are accepted. Every Docker argument is generated by typed code from the selected context, node identity, edition, and bounded port choices. The server binds only to `127.0.0.1`, uses four named volumes, bounded CPU, memory, and PID limits, `no-new-privileges`, and dropped capabilities. Credential output never enters logs, job progress, project files, exports, history, telemetry, or public records.

## Verification boundary

The implementation lane intentionally ran no tests, type checks, lint, builds, packaging, installer execution, runtime interaction, accessibility or security reviews, or UI captures. The source and documentation record the feature contract, but the runtime and built-artifact behavior remain unverified until the release lane runs its own checks.
