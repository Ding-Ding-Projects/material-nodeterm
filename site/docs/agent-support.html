Agents

Agent support

nodeterm is a pluggable multi-agent system — Claude Code, Codex, Gemini, opencode, and Grok all get first-class status badges, session-name syncing, and canvas control, driven entirely by each agent CLI's own hooks rather than by parsing terminal output.

Behaviour

An agent node's live state (working, waiting for you, blocked, or done) comes from a normalized event stream fed by each agent's own hook mechanism, posted to a small local loopback server the app runs. A busy-to-idle transition while the window is unfocused marks the node unread and can fire a desktop notification. Capable agents also expose subagent visualization, context-window metering, session-name syncing between the CLI and the node's title, and — for Claude specifically — branching a conversation into a new resumed session.

Custom, user-defined agents (anything not built in) still get a launch command and a terminal-title-derived status, just without the hook-driven extras.

When enabled in Settings → Notifications, an authenticated agent may run notify --node <id> to signal a linked agent to check its configured coordination inbox. The command submits one fixed prompt only: it cannot carry a subject, transcript excerpt, or caller-supplied text. The target node becomes unread and the notification centre offers an Open agent action without exposing conversation content.

Context-window progress

Every agent card, including custom, resumed, grouped, minimized, restored, kanban, and ephemeral subagent cards, carries a progress track at its top edge. Claude Code, Codex, and Gemini read their own local transcript telemetry and show exact used, total, remaining, and percentage values. Grok, opencode, custom agents, and sessions without a verified reading show explicit unknown, not reported, stale, or unavailable text instead of a fabricated percentage. Provider and source identity, producer epochs, and monotonic generations fence delayed readings, while context values stay in local application data rather than portable project files, exports, captures, logs, or provider prompts.

Read the context-window meter article for the provider matrix, lifecycle ordering, bounded locators, and accessibility details.

Configuration

Per-agent permission mode (how readily the agent may act without asking) is configurable globally and per-project, on whichever agents support the concept. Managed Claude accounts let you run several signed-in identities side by side, each in its own config directory.

The linked-agent inbox signal is off by default. It is additionally subject to the existing project consent, authenticated ownership checks, idle delivery queue, and per-source-target flow budget.

Failure modes

An agent capability is a membership list, not a hardcoded check — a feature meant for one agent should never silently light up for another that merely resembles it. A guess an agent's status can't confidently make (an unreadable hook payload, an unsupported CLI version) degrades to "unknown," never to a fabricated status.

Security considerations

Each terminal node's hook identity is a capability derived from a restart-stable secret local to the machine, never sent anywhere off it; hook payloads are validated before being trusted for anything sensitive like canvas control.

The notification record stores only stable project and node identifiers plus fixed local copy. Runtime callbacks and transcript text are excluded from persistence and export, and display-only lineage ropes never authorize a signal.

Verification

Each agent's hook dialect (event names, field shapes, quirks) is measured against the real CLI rather than assumed from another agent's behaviour, and recorded in a dedicated per-agent document alongside its own device checklist.
