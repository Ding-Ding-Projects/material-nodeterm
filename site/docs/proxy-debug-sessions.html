Browser

Proxy and isolated debugging browser sessions

The isolated debugging browser node starts a supported Chromium browser with a fresh profile, an optional validated proxy, and a loopback-only DevTools Protocol endpoint.

Behaviour

Choose New isolated debugging browser… from the canvas context menu. The guided node provides a session name, an HTTP(S) start URL, an optional proxy, and a detected browser choice. It accepts no shell command, raw request, arbitrary executable path, or extra flags.

Every run creates a new profile, disables sync and extensions, binds CDP to 127.0.0.1, and waits for exactly one matching page target. A second page, extension target, restored page, mismatched URL, or non-loopback websocket is an isolation failure.

Proxy validation

  • Supported schemes are http, https, socks4, and socks5.
  • Hosts are bounded DNS names, IPv4 addresses, or bracketed IPv6 addresses.
  • Ports must be integers from 1 through 65535.
  • Userinfo, paths, fragments, control characters, malformed IPs, and out-of-range ports are refused.

Portable project data

The project stores only the versioned label, normalized HTTP(S) URL, and proxy intent. Profile directories, process ids, local ports, websocket URLs, cookies, local storage, provider sessions, and credentials remain on the local computer. Import performs no launch, network request, proxy connection, or provider mutation.

Failure and recovery

When no supported browser is detected, the node remains available for safe configuration and explains why Start is disabled. If startup times out or target isolation fails, nodeterm stops the owned child, removes the fresh profile, and reports the exact failure. Retry creates another fresh profile.

Security considerations

CDP is a powerful local control surface, so it is never bound beyond loopback. The target list must contain exactly one page with the exact requested URL and a loopback websocket. The normal browser profile is never reused, and credentials are never read or copied.
