Remote and hosted services

GitLab Server hosting

Provision GitLab Community Edition or Enterprise Edition as a guided local service node. The app owns the image profile and Docker arguments, so there is no arbitrary image, environment, Compose, entrypoint, or shell field.

Private-first setup

Select a pinned official release, choose a bounded host port, and let the app check Docker, free capacity, and port availability before creating anything. The service binds only to 127.0.0.1 and keeps four persistent volumes for configuration, logs, application data, and backups.

Readiness and initial credential

The status surface probes the local /users/sign_in route and distinguishes starting, ready, stopped, and error states. A root credential is created in a protected secret file and can be handed off to the owner exactly once. It is not written to the project file or logs.

Recovery lifecycle

Use the node's guided controls for backup, restore, update, rollback, and stop. Restore and stop require the app's two-key confirmation surface. Updating changes only the pinned container image and retains all four volumes. The tunnel handoff appears only after the local readiness check passes, leaving external exposure as a separate explicit decision.

Portability

Project files carry only the node's safe identity, layout, label, and profile intent. Container names, volume names, host paths, secret state, backup metadata, and runtime state stay in local application data. Importing the project performs no deployment or network call and offers an explicit configure route on a new machine.
