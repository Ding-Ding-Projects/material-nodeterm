Terminals · tmux

Terminal sessions & continuity

Every terminal node on the canvas runs inside a persistent tmux session on a dedicated socket, so the session — and whatever is running inside it — survives an app restart and even a full machine reboot.

Behaviour

Each terminal is created with tmux new-session -A -D -s nt-<nodeId> on a socket dedicated to nodeterm, using a generated tmux.conf so the user's own ~/.tmux.conf never interferes. Because the tmux server keeps running independently of the app, a session stays alive with no client attached — closing the app, switching projects, or the OS going to sleep all just detach the client; the process underneath keeps going.

tmux owns the mouse: the wheel scrolls tmux's own history, panes run on the alternate screen (so a full-screen TUI's input line doesn't scroll away), and a drag copies through tmux's copy-mode. Copies leave the terminal via OSC 52, which the app's terminal emulator intercepts and writes to the system clipboard — the one copy path that also works over SSH, since there is no local pbcopy involved.

Configuration

  • Scrollback length, whether tmux is used at all, and the offscreen-release timer are all in Settings → tmux.
  • If tmux isn't found in the usual places, is disabled in settings, or the install path was missed, the app falls back to a plain shell — sessions still work, but they don't survive an app restart.

Failure modes

A machine reboot kills the tmux server, not just the app's client — every session is genuinely gone at that point. The app detects this at reattach time (tmux has-session before spawning) and reconstructs what it can instead of pretending the old process is still there: it replays a byte-capped scrollback snapshot taken shortly before the loss, and — for a resumable agent CLI — relaunches the agent with its own --resume flag against the session id it remembers, rather than starting a blank conversation.

Security considerations

tmux sessions run under the same user account as the app; there is no sandboxing beyond what the OS and shell already provide. SSH-backed sessions run on the remote host's own tmux, reached only through that project's ControlMaster connection.

Verification

Verified by opening a terminal, running a long-lived process, fully quitting the app, relaunching, and confirming the process and its output are still there; and separately by simulating a reboot (killing the tmux server directly) and confirming the scrollback-replay + agent-resume path kicks in instead of a silent blank pane.
