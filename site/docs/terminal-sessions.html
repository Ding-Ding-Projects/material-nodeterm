Terminals · persistence

Terminal sessions & continuity

Terminal nodes use a persistent backend instead of tying the live shell to the desktop window. macOS, Linux, and SSH sessions use tmux; stock Windows uses nodeterm's standalone session host. Both keep the live process running across an app close or crash. Neither keeps that process alive through a machine reboot.

Behaviour

On the tmux path, each terminal is created with tmux new-session -A -D -s nt-<nodeId> on a socket dedicated to nodeterm, using a generated tmux.conf so the user's own ~/.tmux.conf never interferes. tmux owns its screen, mouse, and scrollback; OSC 52 carries copied text back to the system clipboard, including over SSH.

On stock Windows, one detached session-host process owns the real ConPTY plus a headless xterm buffer for each named session. Closing the app, switching projects, or releasing an off-screen terminal detaches the client without ending the process. Reopening the node or relaunching nodeterm reattaches and receives the reconstructed screen.

Configuration

  • Scrollback length, persistent-backend support, and the offscreen-release timer are in Settings → tmux.
  • Settings → Shell on Windows selects the detected default profile. A selected profile is snapshotted per node, and explicit missing profiles fail closed instead of silently falling back.
  • With persistent support enabled, stock Windows selects the standalone session host when no usable native tmux exists. If persistence is disabled or unavailable, the app reports the non-persistent state instead of claiming continuity.

Failure modes

A machine reboot kills the tmux server and the Windows session host, so every live session process is genuinely gone. On the next launch nodeterm reconstructs what it can instead of pretending otherwise: it replays a byte-capped scrollback snapshot and, for a resumable agent CLI, relaunches the agent against the remembered conversation id.

On Windows, an attach is provisional until authentication and the correlated host response succeed. A rejection remains non-persistent and does not open a plain shell or another profile as a substitute.

Security considerations

Persistent sessions run under the same user account as the app; there is no sandboxing beyond what the OS and shell provide. SSH-backed sessions run on the remote host's own tmux. The Windows session host authenticates local clients, while shell executable paths and arguments remain private to the trusted desktop core.

Verification

Resolver, spawn, protocol, reconnect, and fail-closed attach behaviour have focused automated coverage. Packaged Windows interaction and capture evidence for a long-running process across a full app relaunch remains pending until the required cheap headless installed-artifact run records it.
