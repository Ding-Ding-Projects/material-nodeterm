GitLab Server hosting

The installed desktop application is the primary runtime. This documentation page explains the hosting node and does not deploy a server itself.

Guided deployment

Choose a discovered Docker context and either the official Community Edition or Enterprise Edition image. The selected image is pinned by digest. The node creates four managed volumes for configuration, logs, data, and backups, then binds HTTP and SSH to loopback addresses only.

The node checks GitLab's /-/readiness endpoint and keeps stopped and unready states distinct from ready. The lifecycle actions are Deploy, Back up, Restore, Update, and Roll back. Restore and rollback require the application's two-key confirmation surface.

Initial credential handoff

After readiness, the node can read GitLab's initial root credential file once and show it to the active user. The value stays in memory, is never persisted or included in progress output, and is hidden when the user closes the handoff.

Portability and safety

The portable project record contains only edition, pinned image reference, loopback binding, and guided port choices. Context names, container and volume identifiers, backup files, credentials, and process state remain on the machine that owns the binding. Import only restores intent and performs no deployment or network call.

There is no arbitrary image field, shell command field, entrypoint field, environment editor, or public binding. Context and backup lists use local plain-text search with an adjacent anchored regex builder.

Verification status

This implementation lane intentionally did not run tests, type checks, lint, builds, packaging, installer execution, runtime interaction, accessibility or security reviews, or UI captures. Those checks remain release-lane work.
