Remote

Remote & SSH projects

Open a project on a remote host over SSH and everything that works locally — terminals, the file explorer, git, the kanban board — runs there instead, over one shared ControlMaster connection.

Behaviour

A remote node is never silently spawned locally as a fallback — if the SSH connection is down, the node shows an offline state with a reconnect action rather than quietly opening a local shell that only looks like the intended remote one.

Configuration

SSH projects are configured once (host, credentials) and the same connection is reused for every terminal, file operation, and git call the project makes, rather than opening a fresh connection per action.

Failure modes

A remote host's tmux socket is distinct from a local one used the other direction (a machine being SSH'd into versus a machine SSH-ing out) — treating them as the same socket is how a kill action could target the wrong session on the wrong machine, and every kill path is deliberately scoped to avoid that.

Security considerations

Credentials and bearer tokens for remote operations are never placed on a command line's argument list, because a remote process's argv can be world-readable on a shared host — they travel by file with restricted permissions or by stdin instead.

Verification

The generated remote shell scripts (for context resolution, usage reads, session memory sweeps) are executed for real under a real POSIX shell in tests against a fake host tree, rather than only reviewed as source text.
