Git

Source control & worktrees

A full source-control panel — stage, diff, branch, commit, push — plus one-step git worktrees bound directly to canvas group frames, so an agent per branch is just a group per branch.

Behaviour

The source-control panel operates on a selected scope: the project's main checkout, or any worktree bound to a group on the canvas. Creating a worktree is one step from the pane menu or command palette; every node created inside its bound frame automatically inherits that worktree's path as its working directory.

Configuration

AI-generated commit messages use a bring-your-own local agent CLI, spawned read-only against the staged diff — there is no built-in model call.

Failure modes

A worktree deleted outside the app is detected and marked stale rather than silently vanishing from the canvas; its frame stays but every destructive action on it (merge, remove) is disabled until it's unbound. A failed git read is never treated as "git reported nothing" — those are kept as two distinct facts throughout, because conflating them is exactly how a transient failure could look like a deleted worktree.

Security considerations

Merging a worktree can optionally push to the remote — that push is disclosed in the merge dialog and is opt-in, off by default, because a push to a shared remote can't be politely undone the way a local operation can.

Verification

Destructive removal paths refuse to operate on a worktree path that resolves to the repository root, the user's home directory, or an ancestor of either, on every code path that can delete one.
