Remote and hosted services

Hosted-service Cloudflare Tunnel handoff

Hosted service nodes use a private-first handoff. The local HTTP(S) origin must answer a real bounded health request before any provider action can be enabled.

How it works

  1. Save the service address and choose a typed local origin candidate.
  2. Verify local health. A timeout or non-success response leaves handoff unavailable.
  3. Choose a Cloudflare account and zone from searchable catalogs, then enter a validated hostname.
  4. Hand off with Cloudflare Access required. A future Cloudflare manager supplies the provider operation.

The panel reports unbound, discovering-origin, checking-local-health, ready, handing-off, connected, failed, and rolled-back states. A failed operation leaves the local service unchanged.

Portability and privacy

Schema 3 carries only private-first intent and the health path. Account, zone, hostname, origin, tunnel, connector, process, machine path, and credential state remain local. Import does not contact Cloudflare, start a process, change DNS, or change an Access policy.

Availability

This lane supplies the typed contract and GitLab desktop panel. Cloudflare API authentication, catalogs, DNS routing, and connector runtimes are separate features. Until those features are connected, the provider action remains disabled with an explanation.

Verification status

This ultra-speed implementation lane did not run tests, type checks, linting, security checks, accessibility review, builds, packaging, installer execution, runtime interaction, or screenshots. A later verification pass must exercise health success and failure, malformed origins, picker search, provider failure, rollback, and import side-effect refusal.
